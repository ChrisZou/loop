# Loop 审阅

一轮一轮来：写方案 → 用户批注 → 按反馈改 → 再审，直到用户不再提意见。用户在哪审有两种方式，**先判断用哪种**：

| | Mac 端 | 手机端（网页） |
| --- | --- | --- |
| 什么时候用 | 用户就在这台 Mac 前 | 用户在手机上、不在电脑前 |
| 怎么发起 | `loop review 方案.md`，本机弹出审阅窗口 | 脚本创建审阅，拿到链接发给用户，用户在手机浏览器里批注 |
| 怎么拿反馈 | 命令结束时打印在标准输出 | 脚本轮询服务器 |

## 0. 判断 Mac 端还是手机端

按顺序看，命中就定：

1. 用户明说了：「我在手机上」「出门了」「发链接给我」「我在外面」→ 手机端；「在电脑前」「弹窗给我」→ Mac 端。
2. 你不在用户的 Mac 上跑（Linux / 云端环境，或者 `command -v loop` 找不到）→ 手机端。
3. 对话是从手机来的：用户通过手机 App 远程操控这个会话、通过 IM（如飞书机器人）给你发消息 → 手机端。
4. 其他情况，用户一直在本机终端里和你对话 → Mac 端。
5. 还是拿不准，就在对话里问一句「你现在在电脑前还是手机上？」，本次会话记住答案，后面几轮不再问；用户中途说换了地方就跟着换。

## 1. 写方案

把要审的内容写成一个 `.md` 文件，放在当前项目里合适的位置（如 `docs/`）或临时目录。第一个 `# 标题` 会作为审阅标题。

写成**方便逐条批注**的样子，用户是选中原文写意见的：

- 每个决定、每个步骤单独一行或一个列表项，别把几件事塞进一大段。
- 把拿不准的地方明确写成问题，不要藏在叙述里。
- 篇幅只放需要审的内容，背景一两句带过。手机上看尤其要短。

两端渲染能力不同：

| | Mac 端 | 手机端（网页） |
| --- | --- | --- |
| 标题、粗体、列表、代码、引用、表格 | ✓ | ✓ |
| 图片 `![说明](路径)` | ✓ 相对路径按方案文件所在目录解析，也支持 http(s) | ✓ 只有 http(s) 和 base64 行内图；相对路径按网页地址解析，画不出来，图片请用网络地址 |
| 任务列表 `- [ ]` | ✓ 点勾，勾选变化随反馈回来 | ✓ 点勾，勾选变化随反馈回来 |
| 链接 `[文字](url)` | ✗ 原样显示，直接写网址 | ✓ 可点 |
| 长度 | 不限 | 最多 30000 字 |

Mac 端路径有空格时写成 `![说明](<图片/架构 图.png>)`。

## 2A. Mac 端：发起和读结果

优先看你的环境有没有**命令超时**：

- **能后台跑、结束时通知你**（如 Claude Code 的 `run_in_background`）：直接阻塞版即可。
- **前台命令有超时**（Codex、Cursor 等）：用 `--detach` + `wait`，不要把一次长审阅塞进一条会超时的命令里。

```sh
# 无超时限制时
loop review 方案.md

# 有命令超时时：先 detach，再 wait（可多次续等）
loop review --detach 方案.md
# → {"id":"…","status":"pending"}
loop wait <id> --timeout 540
```

`loop review` / 后台 waiter 会**一直等到**用户点「提交」或关掉窗口，常常要十几分钟甚至更久。不要用 `open`、AppleScript 或界面自动化去打开 Loop、粘贴内容；就用这些命令。可以同时开多份审阅。

发起后在对话里告诉用户一句：已经打开审阅窗口了。

`loop wait`：

- 能后台运行并收到结束通知的，后台跑，把 `--timeout` 设大（如 `86400`），停下等通知。
- 只能前台、有超时的，用不超过超时的 `--timeout`；退出码 2 就再调一次 `wait`，直到拿到反馈。别在两次之间自己 sleep。

| 退出码 | 含义 | 怎么做 |
| --- | --- | --- |
| 0 | 用户点了「提交」，标准输出是反馈 | 见第 3 步 |
| 1 | 用户没提交就关了窗口（stderr：`loop: 未提交`） | 不要自动重开。问用户是要继续审、改了再审，还是先不审了 |
| 2 | `wait` 到点了还没提交 | 再调 `wait` |
| 64 / 66 | 用法错误 / 文件读不到或为空 / 会话 id 不存在 | 检查路径和内容后重试 |
| 69 或 `command not found` | 没装 Loop | 已有 Loop.app 的，让用户打开一次，按提示安装；否则让用户构建：`cd <loop 仓库>/mac && ./build-app.sh && ln -sf "$PWD/bin/loop" ~/.local/bin/loop`；用户此时不在电脑前就改走手机端 |

## 2B. 手机端：创建网页审阅、发链接、等反馈

脚本在本 skill 目录的 `scripts/web-review.mjs`（Node 18+，无依赖）。

```sh
# 创建审阅：--agent 写你自己的名字（如 Claude Code、Codex），下一版加 --parent <上一版 reviewId>
node <skill 目录>/scripts/web-review.mjs create 方案.md --agent "Claude Code"
# → {"reviewId":"…","revision":1,"reviewUrl":"https://loop.example.com/?review=…"}

# 等反馈：最多等 --timeout 秒（默认 540）
node <skill 目录>/scripts/web-review.mjs wait <reviewId> --timeout 540
```

1. `create` 后把 `reviewUrl` **发给用户**：用户在这个对话里能看到（手机远程操控、IM 对话），就直接在回复里给出链接；用户看不到这个对话，就用用户惯用的消息渠道发（用户的全局指令里有约定就照做，比如飞书）。说一句「在手机上打开，选中原文写批注，写完点提交」。
2. 然后 `wait`：
   - 能后台运行并收到结束通知的，后台运行，把 `--timeout` 设得很大（如 `86400`），停下等通知。
   - 只能前台运行的，用不超过命令超时的 `--timeout`；退出码 2 就再调一次 `wait`，直到拿到反馈。别在两次之间 sleep，`wait` 自己会每 5 秒查一次。
   - 等了很久（比如一小时以上）还没提交，在对话里问一句用户是否还要审，别无限等下去。

| 退出码 | 含义 | 怎么做 |
| --- | --- | --- |
| 0 | 用户提交了，标准输出是反馈 | 见第 3 步 |
| 2 | 到点了还没提交 | 再调 `wait` |
| 64 / 66 | 用法错误 / 方案读不到、为空或超过 30000 字 | 修正后重试 |
| 69 | 没有 Agent Token 或服务地址 | 请用户把托管服务的 `LOOP_AGENT_TOKEN` 写进 `~/.config/loop/agent-token`（权限 600）、服务地址写进 `~/.config/loop/url`，或设成环境变量 `LOOP_AGENT_TOKEN`、`LOOP_URL` |
| 1 | 网络或服务端错误（stderr 有原因） | 把原因告诉用户 |

网页版至少要有一条批注、改一处待办勾选或写总体意见才能提交，所以用户认可时通常是总体意见里写「可以」「没问题」之类，按意思判断；只提交了勾选也算有反馈。

## 2C. MCP（可选）

仓库 `mcp/server.mjs` 提供 stdio MCP：`loop_web_create` / `loop_web_wait` / `loop_mac_detach` / `loop_mac_wait`，行为与上面脚本和 CLI 相同。已配置 Loop MCP 时优先用工具，不必再手敲命令。详见 `mcp/README.md`。

## 3. 读反馈

**Mac 端用户认可**：输出正好是 `我看过了这版方案，没有修改意见，可以按这版继续。`，审阅结束，按这版继续做。

**有反馈**时格式如下，两端基本一致，各部分没有就不出现：

```text
以下是我对你方案的逐条反馈，请据此修改出下一版：
（「附图」是本机上的图片文件，请打开查看。）

1. 原文：
   > 用户选中的原文（已去掉 Markdown 符号；图片写成 [图片：说明]）
   意见：用户的意见
   附图：/Users/…/attachments/…/xxx.png

待办的勾选状态改为：
- [x] 方案 A：…

总体意见：…（多条时是编号列表）
```

- 按原文定位到方案里的位置，逐条处理；条目按原文顺序排列。
- `附图：` 是用户截图的本机路径（只有 Mac 端有），**一定要打开看**。
- 勾选状态是用户对 `- [ ]` 选项的决定，两端都有，下一版照此更新。
- 只有 `意见`、没有明确改法的，按你的判断改；真有两种以上合理理解、改错代价大的，在下一版里写成选项让用户选，而不是在对话里停下来问。

## 4. 改完再审

1. 直接修改同一个文件，出下一版。每一条意见都要落实，不能悄悄跳过；不同意的，在对应位置写明理由。
2. 在对话里用几行列出这版按反馈改了什么（第几条 → 怎么改的）。
3. 再发起一轮：Mac 端再次 `loop review` 同一个文件；手机端用 `create … --parent <上一版 reviewId>` 建新版本，把**新链接**发给用户（每一版链接都不同）。

一直循环，直到用户认可，或者用户在对话里说可以了、不用再审。
